# Roadmap

## Where things stand

Three devices are first-class and hardware-verified: the Fractal AM4, the Fractal Axe-Fx II XL+ (model byte 0x07, confirmed on Quantum 8.02 firmware), and the ASM Hydrasynth Explorer. On those, preset and patch authoring is audio-confirmed end to end: you describe a tone in chat and the server builds it on the device. The modern Fractal floor family is in community beta: the Axe-Fx III (model byte 0x10), the FM3 (0x11), and the FM9 (0x12) run on one shared gen-3 codec with per-device parameter catalogs mined from each unit's own editor. Their wire shapes are byte-verified against Fractal's published "MIDI for Third-Party Devices" v1.4 spec and a growing set of public + community-hardware captures. The FM3 is the most hardware-verified of the family: a 2026-06-12 community field test ran this server's own probes over the FM3's USB-serial transport and confirmed discovery, framing, the entire read path, continuous parameter writes, bypass, scene switching, and preset switching end-to-end, and a 2026-06-10 collaborator session confirmed set-by-name discrete parameter writes on FM3 hardware via frames byte-identical to this server's encoder. `set_block` placement, `save_preset`, and the Windows serial-driver path still await on-device confirmation. The FM9 has community captures confirming its model byte, reads, preset receive, scene/preset switching, and status framing, plus a 2026-06 owner test that round-tripped reads and continuous writes on the device; the Axe-Fx III shares the byte-verified codec and had its first owner round-trip in 2026-06 (reads and continuous writes confirmed on hardware), with discrete set-by-name, save, block placement, and the live grid read still community beta. Gen-3 tool responses carry an unverified-on-hardware notice only for ops not yet confirmed on that device. The Fractal VP4 (0x14, gen-3 codec but AM4-shaped) ships reads plus community-beta writes (continuous-knob set_param/set_params with raw wire values, set_bypass, and save_preset, decoded byte-exact from a fw 4.03 community capture, untested on hardware); set_block placement, scene switching, preset switching, and enum/TYPE sets stay gated until their wire shapes are decoded (block placement awaits a serial block-placement capture). The first-generation Fractal Axe-Fx Standard/Ultra is also in community beta (its own nibble-split codec, model byte 0x01), decoded byte-exactly from Fractal's published gen-1 SysEx spec. Both parameter writes and parameter reads are wired: a query (function 0x02 with the set/query flag cleared) returns the live value and the device's own label, and `get_preset` returns the spec-pinned patch-dump subset (name + effect-grid layout + source flag). None of the gen-1 path is confirmed on real hardware, so values should still be confirmed on the front panel. Four non-Fractal devices are also in community beta, proving the descriptor model scales past guitar amps. The **Novation Circuit Tracks** is a groovebox sequencer: it authors drum grooves and melodic note tracks (live-streamed over MIDI clock or written into a `.ncs` project uploaded to a slot), uploads WAV samples and whole projects, imports a real song's groove from Songsterr / a drum tab / a MIDI file, and can sequence outboard gear out of its MIDI tracks (a programmed drum groove routed to a Roland SPD-SX's pads, for instance); it also saves an edited synth patch to a Flash slot and reads a stored patch back (`save_preset` / `get_preset("patch:N")`). Owner-confirmed on hardware: live streaming to the synths, the `ncs_upload` authoring of a beat plus note tracks onto a stored project that loads and plays on the device, sample upload, and the synth-patch save/read round-trip. The **Roland SPD-SX** is a sample pad on a hybrid transport: in WAVE MGR mode it is a USB mass-storage volume whose kits and wave pool are authored by the unified verbs (`scan_locations`, `get_preset`, `list_samples`, `export_preset`, `upload_sample`, and the new `author_kit`), and in AUDIO/MIDI mode `switch_preset` recalls a kit and `apply_pattern` triggers pads; the storage codec is byte-identical to the device's own files and hardware-confirmed via the Python pipeline it was ported from, with the write path through the server itself awaiting an on-device pass. The **Boss VE-500** vocal processor is decoded byte-exact from the manufacturer's own editor source (873 parameters across 41 blocks, zero captures) and is hardware-verified on the maintainer's unit: parameter set/read, bypass, user-memory recall, whole-patch `apply_preset` (enum/type values resolved by editor panel labels), and `save_preset` to a user memory (it sends the editor's Communication Mode ON handshake before the store, then waits for the device's store-ack echo) are confirmed end-to-end, with factory preset P01-P50 recall (its bank mapping undecoded, gated) and whole-patch reads deferred. The **Boss RC-505mk2** Loop Station is a looper on a hybrid transport, like the SPD-SX: in normal USB-MIDI mode `switch_preset` recalls a memory (memory M to Program Change M-1 on the RX CTL channel, device-confirmed) and looper/track functions are driven by CC through the memory's own ASSIGN table, and in storage mode its memories are `.RC0` files the server reads (`scan_locations`, `get_preset(location)` decodes the ASSIGN control-routing table) and authors. Authoring reuses the existing `apply_preset(target_location, save_authorized)` verb (its spec is the exact inverse of the `get_preset` read), honoring the device's own A/B `<count>` double-buffer save and backing up the overwritten copy first. The `.RC0` codec and the RC-505mk2 ASSIGN dictionary are byte-exact against real device files and hardware-confirmed end-to-end: a scene ping-pong authored into a memory triggered track play/stop over MIDI on the unit, confirmed by ear and front panel. Beyond the registered devices, generic-MIDI primitives (CC, NRPN, SysEx, program change, notes, clock, and more) reach any USB MIDI device the OS exposes, so synths, looper pedals, and other gear are usable from day one.

## Milestones

### Done

- **Workspace and codec split.** The pure wire codec lives in its own package, `fractal-midi`, published to npm with no MIDI transport and no MCP code. The MCP server packages depend on it. The codec is reusable by other consumers and testable in isolation.
- **Multi-device unified tool surface.** One port-dispatched verb set (`set_param`, `get_param`, `apply_preset`, `translate_preset`, `get_preset`, `switch_preset`, `save_preset`, `switch_scene`, `set_block`, `set_bypass`, `lookup_lineage`, `scan_locations`, `describe_device`, `find_compatible_types`, and the batch read/write pair) works across every registered device. Adding a device is a descriptor plus a wire adapter, not a new set of tools. The earlier device-namespaced tools have been removed in favor of this surface.
- **Recipes, mod-matrix, and macro routing.** Named recipes start a build from a curated point: `recipe_id` on `apply_preset` for the linear guitar devices, and on `apply_patch` for the Hydrasynth. The Hydrasynth ships a patch library auditioned on hardware (Prophet-5 pad, Juno-106 pad, OB-Xa Jump, and others); the guitar side ships utility effect recipes (pitch, wah, filter, auto-wah, diatonic pitch). The voice-class tools (`set_mod_route`, `set_macro_route`, `set_macro`) wire a synth's modulation matrix and performance macros by name, so an agent can build a voice that moves, not just a static set of knobs.

### In progress (help wanted)

- **Modern Fractal family (Axe-Fx III / FM3 / FM9) to first-class.** The protocol layer is written and hardware confirmation is accumulating per device. The FM3 is closest: a 2026-06-12 community field test confirmed its serial transport, full read path, continuous parameter writes, bypass, scenes, and preset switching end-to-end through this server's own probes, and a 2026-06-10 collaborator session confirmed set-by-name discrete writes via frames byte-identical to this server's encoder. What remains for first-class is on-device confirmation of `set_block` placement and `save_preset` (one verify-probe re-run on a Drive-free preset plus one manual save test), a Windows serial-driver run, and the FM3 editor cache file for device-true display ranges. The FM9 has broad capture coverage (model byte, reads, preset receive, scene/preset switching, status framing) plus a 2026-06 owner round-trip of reads and continuous writes; the III had its first owner round-trip in 2026-06 (reads and continuous writes confirmed), leaving discrete set-by-name, save, block placement, and the live grid read as the community-beta gaps. Hardware-runnable probe scripts and per-device capture guides (`packages/fractal-midi/docs/capture-guides/`) target the highest-value gaps; fixes and capture data move each device from community beta to hardware-verified.

- **Roland SPD-SX kit + sample authoring (hybrid transport).** The SPD-SX is a USB mass-storage device in WAVE MGR mode: its kits and wave pool are XML `.spd` files on a mounted drive, decoded byte-exact and hardware-confirmed via a Python pipeline that built playable kits on the device, now ported byte-faithfully to TypeScript. Rather than a device-specific tool family, the SPD-SX is one **hybrid-transport descriptor** driven entirely by the unified surface: the dispatcher resolves the live USB mode per call (drive mounted → storage, else a MIDI port → MIDI). In WAVE MGR mode a kit is a stored preset addressed by location, so `scan_locations` lists kits, `get_preset(location)` reads a kit's pad map, `list_samples` reads the wave pool, `export_preset(location)` backs up a kit, `upload_sample` appends a wave, and the new sampler verb `author_kit` writes the pad→wave map. In AUDIO/MIDI mode `switch_preset` recalls a kit and `apply_pattern` triggers pads. A verb invoked in the wrong USB mode returns a clear capability error naming the mode to switch to. The codec is byte-identical to the device's own files (golden-verified, plus a descriptor-level test exercising the storage reader/writer + mode guards); the write path through the server itself awaits an on-device confirmation pass.

- **Novation Circuit Tracks: groove + melody sequencing to first-class.** `apply_pattern` authors drum grooves and melodic note tracks (synth and MIDI-out), live-streamed over MIDI clock or written into a `.ncs` project uploaded to a slot, with per-step sample flips, micro-step buzz rolls, and scale-aware authoring. Song grooves import from Songsterr, a drum tab, or a MIDI file; WAV samples and whole projects upload to the device; the drum-track→sample binding is decoded so a groove targets specific kit voices; and `external_targets` routes a pattern out to outboard gear (e.g. the SPD-SX). A synth patch also saves to a Flash slot and reads back from the bank (`save_preset` / `get_preset("patch:N")`). Owner-confirmed on hardware (2026-06): `live_stream` melodies/chords on Synth 1/2, the `ncs_upload` authoring of a beat plus note tracks onto a stored project that loads and plays on the device clock, sample upload, and the synth-patch save/read round-trip. Drum tracks cannot record external MIDI, so `ncs_upload` (not live capture) is the drum-onto-device path, and `record_capture` stays synth-track-only and unadvertised. The remaining gaps are synth CC/NRPN writes, breadth of song coverage, and the in-project pattern-select MIDI dead-end.

- **Boss VE-500 Vocal Performer (hardware-verified).** The full wire protocol (model ID, envelope, Roland checksum, address map, value packing) was decoded byte-exact from the manufacturer's own editor source, so the catalog (873 parameters across 41 blocks) needed no captures. `set_param`/`set_params`, `get_param`/`get_params`, `set_bypass`, `switch_preset` (user memories), whole-patch `apply_preset` (enum/type values resolved by editor panel labels), and `save_preset` to a user memory are confirmed end-to-end on the maintainer's unit (`save_preset` sends the editor's Communication Mode ON handshake before the store, then waits for the device's store-ack echo). What remains is whole-patch reads and factory preset (P01-P50) recall (its bank mapping undecoded, gated), both deferred.

- **Boss RC-505mk2 Loop Station: looper support (hybrid transport).** The RC-505mk2 is a class-compliant USB-MIDI device in normal mode and a USB mass-storage volume of `.RC0` memory files in storage mode, registered as one **hybrid-transport descriptor** driven entirely by the unified surface. Live: `switch_preset` recalls a memory (Program Change on the RX CTL channel, device-confirmed), looper/track functions ride CC through the memory's user-configured ASSIGN table (send them with `send_cc`), and it slaves or masters the MIDI clock. Storage: `scan_locations` lists memory names, `get_preset(location)` decodes a memory's ASSIGN control-routing table, `export_preset(location)` backs up the live `.RC0`, and authoring a memory's name + ASSIGN table reuses `apply_preset(target_location, save_authorized)` (a FRESH-BUILD, the inverse of the read), with the device's A/B `<count>` double-buffer save and backup-before-write baked in. The `.RC0` codec and RC-505mk2 ASSIGN dictionary are byte-exact against real device files and the whole path is hardware-confirmed end-to-end (a CC-driven scene ping-pong authored into a memory started/stopped looper tracks on the unit). The unit never echoes state over MIDI, so live control is send-and-confirm-by-ear; remaining work is broadening the decoded ASSIGN targets past the per-track set (CUR.TRK / global transport / FX / mixer) and the CC#01-31 source base.

### Next (demand-driven)

- **Expansion beyond Fractal.** The descriptor model is built so a new device is a schema plus a wire adapter, not new tools. The natural next targets are popular amp modelers that publish their MIDI specifications (Line 6 Helix and similar) and other high-demand gear. Which device comes first is driven by demand: if owners ask for a specific modeler or synth and the protocol is documented, it moves up. Generic-MIDI primitives already cover the basics for anything with a published CC chart in the meantime.

## Decisions log

| Date | Decision | Rationale |
|---|---|---|
| | Publish the wire codec (`fractal-midi`) as its own npm package, separate from the MCP server. | Keeps the domain core free of MIDI I/O and MCP framework concerns, so it stays testable in isolation and other consumers can use it without pulling in the server. |
| | Unified, port-dispatched tool surface; adding a device means writing a descriptor, not new tools. | The public surface stays small and learnable while device coverage scales. Unsupported operations fail as capability checks rather than missing endpoints. |
| | Display-first tool I/O on every device, including enum option strings. | Tools speak front-panel units (0..10 knob, dB, ms, ratio, enum name); wire encoding never leaks through tool I/O. A parity gate round-trips every value and fails the build on any leak of an internal index or wire byte. |
| | Local stdio transport. | The server runs on the user's machine next to the USB MIDI hardware. No network surface, no cloud dependency, and the user's presets and gear stay local. |
| | Build to the current Model Context Protocol revision (2025-11-25). | Structured tool output with declared output schemas, the four behavioral annotation hints on every tool (gated in CI), and actionable error shapes so the agent can self-correct in one turn. A later release candidate exists but is not yet current stable, so we target the shipped revision. |
| | Remove the device-namespaced tools in favor of the unified surface. | Two parallel surfaces meant duplicated guidance and a larger thing to learn. The behavioral guidance now lives in each device's `describe_device` response, so the unified verbs carry it without a second tool family. |
| 2026-06-27 | Tools scale with capability ARCHETYPES, not with devices. No hard tool cap; no device prefixes; a new bare verb only for a genuinely novel capability. | The real cost of the tool surface is the per-turn context tax + model selection accuracy, not a round number. Devices land as descriptors on shared archetype verbs (preset / patch / pattern / sampler / looper); per-device vocabulary lives in `describe_device`. See [docs/design/device-archetypes-and-transport.md](docs/design/device-archetypes-and-transport.md). |
| 2026-06-27 | Unify the verbs, never the archetypes. | The shareable layer (params + preset-container + sample-pool) is already the base unified surface every device uses. A combined sequencer/sampler/looper tool family would force each description to hedge across three runtime models, hurting tool-selection. Archetype-specific runtime verbs stay separate and minimal. |
| 2026-06-27 | Multi-device song setup = agent orchestrates over mechanical tools (not a reasoning mega-tool). | Keeps the musical reasoning in the model (so it improves as models improve) and the closed/dangerous parts (transport, port arbitration, acks) in code. A future `apply_setlist` persists a *resolved* config the agent already computed: a cache of intelligence, not its source. |
| 2026-06-27 | Generalize the transport abstraction at `DispatchCtx`/`openCtx` (add `transport` to the descriptor); SPD-SX becomes one hybrid descriptor. | USB mass storage is a mounted filesystem, not a MIDI byte stream, so it can't be a `MidiConnection` (where serial already lives), it generalizes one level up. Hybrid (one descriptor, mode resolved at call time) matches how a user thinks ("my SPD-SX"). This is also step one of the connection arbiter the song-orchestration vision needs. |
| 2026-06-27 | Add `describe_rig`: a read-only whole-rig overview (every registered device + best-effort connectivity + transport/class/tier/pattern-target + one-line summary). | The agent-orchestrates-the-rig model (Option B) needs a "see the whole stage" read before it can plan a multi-device setup; `list_midi_ports` is raw OS ports and `describe_device` is one device at a time. Opens no handles. Hardware-validated via Claude Desktop (10 devices, SPD-SX resolved as a mounted drive). |
| 2026-06-27 | Connection arbiter design locked (reviewed by a 5-lens workflow): **handle-health (R2) ships first**; per-endpoint serialization (R1) + contention/cancellation (R3) are the orchestration foundation; the lock lives at the **`openCtx` seam** keyed by `connection_label`; use **`async-mutex`**; capacity/rotation **cut**. | The review found the original framing mis-attributed the logged dead-port/reboot incidents (those are cross-process + poisoned-handle = R2/health, which an in-process mutex can't fix) and that wrapping every `execute*` would bypass `openCtx` and self-deadlock on composite/multi-endpoint ops. Cross-process coordination is explicitly out of scope (deferred to a future lockfile/named-mutex). Full design + test plan: [docs/design/connection-arbiter.md](docs/design/connection-arbiter.md). |
| 2026-07-08 | Boss RC-505mk2 looper authoring reuses `apply_preset(target_location, save_authorized)`, NOT a new bare verb. | Unlike the SPD-SX kit (a pad→wave map with no preset shape, which earned the new `author_kit` verb), an RC memory IS preset-shaped: a name + a table of slots each carrying params, exactly `PresetSpec`, and `get_preset` already emits that shape, so authoring is its literal inverse. Reusing the existing verb keeps the tool surface flat (a stated value) with no new selection-accuracy tax. The storage device is bufferless, so `save_authorized: false` is read as a no-write preview and `save_authorized: true` as the file write; the A/B `<count>` double-buffer arbitration + backup-before-write live in the writer. |
| 2026-07-27 | A pattern owns its own note DURATION; the receiving instrument owns only timbre. Mini-notation gains `:len` (steps) and `_` (tie), and `preserve_template_gates` defaults to preserving when re-authoring over an existing project. | Without a stated length, every authored note is a one-step trigger, so a "pad" borrows its sustain from whatever synth happens to be receiving and becomes a blip the moment that instrument is swapped. Length is authored in STEPS because that is the unit the device's own Gate View shows (display-first); the neutral field underneath is sixths of a step and stays internal. A length that is not a whole sixth is refused rather than rounded, so the failure lands at the authoring boundary instead of silently moving a note. Preserving by default because a re-author previously flattened every hand-dialled length in the target project, and the destructive direction should be the one you ask for. Rejected: Strudel-style elongation, which consumes grid cells and therefore cannot express a sixteen-step drone in sixteen steps nor sub-step staccato. |
| 2026-07-27 | A tool schema key that no handler reads is a BUILD FAILURE, enforced by a static AST check in the dispatcher verifier. | A tool schema is the contract an agent reads and trusts, so a parameter that exists, validates, and then does nothing is a lie the agent cannot detect. `apply_pattern` declared two such keys while their entire downstream implementation existed and worked. Neither the type checker nor `tools/list` can catch it: the handler's parameter type is INFERRED from the schema, so omitting a key is perfectly well typed and the tool still lists with the parameter present. It is the sibling of the existing schema-to-executor contract test: that one asks whether the executor accepts what the schema accepts, this asks whether the handler passes on what the schema declares. |
| 2026-07-27 | In the shared MIDI transport, the OUTPUT port closes before the INPUT port, each close is isolated, and a throwing input close is never retried. | The Windows output close has no error path, while the input close can raise when unpreparing a header on a handle poisoned mid-SysEx, and the binding does not wrap it. With input first, one throwing input close aborted the whole teardown and leaked the OUTPUT port for the life of the process, so the next connect failed its own port-open assertion against our own leaked handle. That, and not the driver, is why a reconnect could never recover a wedged handle and only a restart cleared it: a limitation this project had documented as driver-level and unfixable. No retry on a throwing input close because the library frees its SysEx buffers before the error return without clearing the vector, so re-entering that path double-frees. |
