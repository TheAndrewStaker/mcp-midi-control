## Device

Boss's vocal performer: a floor unit with harmony, pitch correction, dynamics,
modulation and a looper, addressed as a chain of effect sections rather than a
grid. It holds 99 user memories, U01 through U99, plus 50 factory presets, P01
through P50. Boss's editor app is the **VE-500 Editor**.

The maintainer owns one, and most of the surface is hardware-confirmed. Its
wire protocol is Roland's, decoded from the editor's own code
(`packages/ve-500/src/descriptor.ts`).

## Confirmed on hardware

On the maintainer's own unit:

- Parameter set and read, bypass, and user-memory recall.
- Whole-patch `apply_preset`.
- `save_preset`, including the Editor Communication Mode handshake that a bare
  store command needs to actually persist.
- SYSTEM and global parameters, written and read back, with the change confirmed
  by what the unit then did rather than by the read alone.
- Reading a stored user memory's parameters at that memory's own address, without
  recalling it and without disturbing the edit buffer. All 874 answered.
- MIDI-note pitch correction driven from a sequencer over DIN, retuning a live
  sung voice for a whole song.
- The loaded memory's number, every user memory's name, and a summary read of
  the loaded memory and of a stored one.

**Please do not re-run these.**

## Worth knowing before you drive this device

- **A save acknowledgement is not proof.** Always verify by reading the value
  back. One session saw a save acknowledge while most of the changed parameters
  did not persist; an identical retry then persisted all of them.
- **If the unit seems not to be receiving, measure what actually arrives before
  you theorise.** `system_midi.midi_usb_out_thru` echoes whatever reaches the DIN
  MIDI In back out over USB, so one reversible write shows you the far end of
  your chain instead of what the upstream gear claims to be sending. On the
  maintainer's rig that found a fault that was in neither device: an intermediate
  synth was absorbing the exact channel the VE-500 had been pointed at, because
  it was that synth's own receive channel. Every readable setting on every device
  was correct throughout.
- **Two copies of the MIDI settings, and the difference is not cosmetic.**
  Several sections that exist per patch also exist at system scope, and a
  preference selects which copy is live. Each copy carries its own bounds. On one
  unit the system copy of the MIDI-to-pitch-correct note zone was narrowed to a
  17 semitone window while the patch copy spanned the full range, so routing
  through the wrong copy would have worked in the middle of the keyboard and
  silently failed at the edges. Read the copy you are about to route through.
- **PC IN off does not stop recall from this server.** A Program Change is
  ignored silently when the unit's PC IN is off, so `switch_preset` reads PC IN
  before every user-memory recall and, when it is off, recalls through the
  current-patch-number register write instead. The server will not turn PC IN on
  for you: that setting is usually off deliberately, to stop a stray Program
  Change on a shared bus recalling a patch mid-song. If the pre-flight read gets
  no answer the register write is used as well, since it works either way.
- **The unit is briefly deaf right after a recall.** A read sent in the first
  few hundred milliseconds gets no answer. `switch_preset` therefore polls the
  loaded memory number until the unit reports the target, and says on the
  receipt whether it moved. Five back-to-back recalls each confirmed in about
  1.1 seconds on the maintainer's unit.
- **Patch names are 16 ASCII characters**, space padded.

## Before you start

Read [../SAFETY.md](../SAFETY.md) once. The device-specific parts:

- **Port exclusivity.** The VE-500 Editor holds the USB port. Quit it fully
  before driving the server. On Windows check the system tray.
- **Two device settings gate preset recall.** The unit's **PC IN** must be ON and
  its receive channel must be OMNI or channel 1. If recall silently does
  nothing, check those two before reporting a bug, and tell us what they were
  set to either way.
- **Saving overwrites a user memory.** Use one you do not care about. A save is
  not reversible.
- **Firmware updates.** Never run Boss's updater while an MCP host holds the
  port.
- **What we will never ask you to do.** No firmware modification, no opening the
  unit, no factory reset.

## Asks, ranked

### SESSION-1: Confirm factory preset recall
**Tier: SESSION | ~5 minutes | changes the loaded patch, nothing is stored | unlocks: `switch_preset` for P01 to P50**

The newest capability on this device and the only recall path nobody has
confirmed. User memories recall by a bare Program Change, which is confirmed.
Factory presets do **not**: they go through a direct write to the
current-patch-number register, decoded from the editor's own patch-switch
handler.

With the VE-500 connected and the editor quit:

> "Switch my VE-500 to factory preset P12."

Check the unit's display. Then try one more, ideally a low number and a high
one, so the addressing is exercised at both ends.

Report whether the patch changed, what the display showed, and your PC IN and
receive-channel settings.

### SESSION-2: Confirm a save on a different firmware
**Tier: SESSION | ~10 minutes | writes and then PERSISTS | unlocks: cross-firmware save confidence**

Save on this device needed a specific fix: a bare store command did not persist
a value set over MIDI until the server started sending Editor Communication Mode
ON first, exactly as the editor's own connect handshake does.

If you are on a different firmware, confirming that still holds is worth
knowing.

Pick a user memory you do not care about. Set one parameter, save to that
memory, switch away, switch back, and check the value survived.

Report your firmware version and whether it persisted.

### REPORT-1: Tell us your PC IN and receive-channel settings
**Tier: REPORT | ~2 minutes | nothing is sent to the device | unlocks: better failure messages**

Two device settings gate preset recall entirely, and a wrong setting produces a
silent failure that looks exactly like a broken wire.

Check your unit's MIDI menu and report **PC IN** (on or off) and the **receive
channel**. Also paste your port list:

> "list the MIDI ports you can see"

This is small, and it directly improves what the server can tell the next person
when a recall does nothing.

## Submitting

See [../SUBMITTING.md](../SUBMITTING.md). For this device, always include:

- VE-500 firmware version,

- the loaded memory or preset,
- **PC IN and receive-channel settings**,

## When an ask closes

1. Move the capability's row in **Support status** to its new status word and
   cite the new evidence.
2. Add a line to **Confirmed on hardware** if a device confirmed it.
3. Delete the closed ask from **Asks, ranked**.
4. Update `capabilities.support_tier` and `capabilities.verification` on the
   descriptor if the tier moved. Preflight fails if the page and the descriptor
   disagree.
5. Update this device's row in [../README.md](../README.md).

The VE-500 shares Roland's wire conventions with other Boss devices here, so a
finding about the envelope or the checksum may also apply to
[rc-505mk2.md](rc-505mk2.md) and [rc-600.md](rc-600.md). Its parameter address
map is its own.
