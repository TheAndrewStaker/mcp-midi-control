## Device

Boss's floor loop station: six stereo tracks, 99 memories, nine footswitches,
and a rhythm and effects section. Boss's companion app is Boss Tone Studio.

Like its tabletop sibling the RC-505mk2, this device has **two surfaces**:

| Surface | How | What it does |
|---|---|---|
| **Live MIDI** | USB or DIN MIDI | Memory recall by Program Change, looper and track control via CC routed through the memory's user-configured ASSIGN table, and MIDI clock |
| **Storage** | The unit mounted as a drive | Reading a memory's name and its ASSIGN routings from its stored files, and renaming a memory |

It shares the mk2's stored-file generation and hybrid transport
(`packages/boss-rc/src/descriptor.ts`), so a lot carries over. **One thing does
not**, and it is the reason authoring is restricted here: the ASSIGN
source-and-target ordinal mapping is undecoded on the RC-600.

The RC-600's published ASSIGN vocabulary is also richer than the mk2's: more
sources, six tracks of per-track targets rather than five, and a large
non-per-track set. None of that vocabulary is wired for automatic lookup, so CC
numbers are driven directly and confirmed by ear.

## Support status

| Capability | Status | Evidence |
|---|---|---|
| Memory recall by Program Change | hardware-unverified | Documented in Boss's RC-600 Parameter Guide. The exact offset, memory M recalling on Program Change M minus 1, is carried from the mk2's hardware-confirmed behavior and standard Boss practice, **not** independently confirmed on an RC-600 (`packages/boss-rc/src/descriptor.ts`, the RC-600 config's `verification`) |
| Looper and track control via CC through a memory's ASSIGN table | hardware-unverified | Documented in the same Parameter Guide |
| MIDI clock | hardware-unverified | Same source |
| Reading memories off the drive: `scan_locations`, `get_preset`, `export_preset` | hardware-unverified | The stored-file envelope, the twelve-character name encoding, the sixteen-slot ASSIGN block shape and the six-track layout are **byte-confirmed** against two real RC-600 device files from an openly licensed corpus |
| Renaming a memory: `apply_preset` with a name, `save_preset` | hardware-unverified | Name encoding is byte-confirmed against those same real files |
| Authoring a POPULATED assign slot | gated | Refuses. The ASSIGN source and target ordinal-to-label mapping is not decoded |
| Reading assign labels | partial | `get_preset` reports raw source and target tokens rather than names, for the same reason |
| Parameter read over MIDI | not supported by the device | The unit never echoes state |

Support tier: `generic-only`. This mirrors `capabilities.support_tier` on the
descriptor at `packages/boss-rc/src/descriptor.ts`, and preflight fails if the
two disagree.

> **Maintainer note: the tier is shared with the RC-505mk2 and cannot currently
> differ.** It is set on the Boss RC descriptor factory rather than per config,
> so both loopers report `generic-only` even though their evidence differs: the
> mk2's storage surface is hardware-confirmed and the RC-600's is byte-confirmed
> against files but never exercised on a unit. Both statements are in
> `packages/boss-rc/src/descriptor.ts`. The contribution-guide gate warns about
> the disagreement rather than failing on it. Resolve it in the descriptor, not
> here.

## Confirmed on hardware

Nothing. This project owns no RC-600.

What has come off real RC-600 hardware, indirectly, is the stored-file evidence:
two genuine device files from an openly licensed corpus, against which the
envelope, name encoding, ASSIGN block shape and six-track layout are all
byte-confirmed. That is strong evidence for the format. It is not a confirmation
that this server reads or writes a real unit correctly.

## Blocked, and on what

| Blocked capability | Missing evidence | Closed by |
|---|---|---|
| Authoring a populated ASSIGN slot | The ordinal-to-label mapping for ASSIGN sources and targets. **Both corpus files hold only blank factory assigns**, so the corpus cannot supply it, and two independent guesses from the manual's ordering contradict each other, which is exactly why nothing is shipped | DONATE-1 |
| Memory recall offset | Whether memory M really recalls on Program Change M minus 1 on this unit | SESSION-1 |
| Everything else | One owner round trip. Not a decode gap | SESSION-1, SESSION-2, SESSION-3 |

## Before you start

Read [../SAFETY.md](../SAFETY.md) once. The device-specific parts:

- **The two surfaces need different states.** Live MIDI control needs the unit
  running normally. Reading memories needs the unit **mounted as a drive**. If a
  storage ask reports "not mounted", that is the mode, not a bug.
- **The unit never tells you anything.** There is no parameter read over MIDI. A
  tool call reporting success has confirmed only that bytes went out. Your ears
  and the front panel are the verification.
- **ASSIGN routings are user-configured.** A CC only does something if the loaded
  memory routes it. A CC that does nothing usually means the memory has no
  assign for it. Check the memory's ASSIGN page before reporting a bug.
- **Firmware updates.** Never run Boss's updater while an MCP host holds the port
  or the drive.
- **What we will never ask you to do.** No firmware modification, no opening the
  unit, no factory reset.

## Asks, ranked

### DONATE-1: Send a memory file with POPULATED assign slots
**Tier: DONATE | ~5 minutes | no device time | unlocks: ASSIGN authoring**

**The highest-value ask on this page**, and it needs no capture tooling, no
device time and no risk.

The two real RC-600 files this project has hold only **blank factory assigns**.
That is the whole blocker: with nothing populated, there is no way to bind an
ordinal to a label, and two independent readings of the manual's ordering
disagree with each other. Rather than pick one and be silently wrong, authoring a
populated assign slot refuses.

A single memory with real assigns in it breaks the deadlock.

1. On the unit, configure a few ASSIGN slots in one memory. Make them
   **distinctive**: different sources, different targets, ideally spread across
   tracks rather than clustered.
2. **Write down exactly what you set**, slot by slot: slot number, source,
   target. This list is the whole point; the file alone is only half the answer.
3. Mount the RC-600 as a drive and copy off that memory's stored file.
4. Send the file plus your written list plus your firmware version.

The pairing of a real file with a known ground truth is what pins the ordinals.
Five populated slots is plenty. Sixteen is better.

### SESSION-1: Confirm memory recall and the offset
**Tier: SESSION | ~5 minutes | changes the loaded memory, nothing is stored | unlocks: `switch_preset`**

The recall offset is inherited from the mk2 and standard Boss practice rather
than confirmed here, and an off-by-one would be invisible in the middle of the
range.

> "Switch my RC-600 to memory 1."

then

> "Switch my RC-600 to memory 99."

then one in the middle.

Report what the display showed for each, plus your unit's receive channel and PC
IN setting.

### SESSION-2: Read your memories off the drive
**Tier: SESSION | ~10 minutes | read-only | unlocks: `scan_locations`, `get_preset`, `export_preset`**

The stored-file decode is byte-confirmed against two real files, and nobody has
run it against a real mounted unit through this server.

Mount the RC-600 as a drive, then:

> "What memories are on my RC-600?"

then

> "What's in memory 5?"

Compare the reported names to the unit's own memory list, and the reported assign
slots to that memory's ASSIGN page. Assign sources and targets will come back as
raw tokens rather than names; that is expected until DONATE-1 lands.

**A wrong name or a wrong slot count is the valuable outcome here.**

### SESSION-3: Drive a looper CC and watch the unit
**Tier: SESSION | ~10 minutes | sends MIDI only, nothing is stored | unlocks: live looper coordination**

Check which control channel your unit receives on, and make sure the loaded
memory has an ASSIGN routing the CC you are about to send. Then send that CC
through the server and watch the looper.

Report: the control channel, the memory number, which ASSIGN slot maps that CC
and to what, and what the looper actually did. If nothing happens, say what the
ASSIGN page shows.

## Submitting

See [../SUBMITTING.md](../SUBMITTING.md). For this device, always include:

- RC-600 firmware version,
- operating system,
- the memory number involved,
- **which surface you used**, live MIDI or the mounted drive,
- the control channel and the relevant ASSIGN routing, for any CC ask,
- for DONATE-1, the slot-by-slot list of what you configured.

## When an ask closes

1. Move the capability's row in **Support status** to its new status word and
   cite the new evidence.
2. Add a line to **Confirmed on hardware** if a device confirmed it.
3. Delete the closed ask from **Asks, ranked**, or reduce it to a one-line closed
   note if the mk2 still needs it.
4. Update `capabilities.support_tier` and `capabilities.verification` on the
   descriptor if the tier moved, and note that the tier currently lives on the
   shared factory rather than per config, so moving it moves both loopers.
   Preflight fails if the page and the descriptor disagree.
5. Update this device's row in [../README.md](../README.md).

The RC-505mk2 shares this device's stored-file generation and hybrid transport,
so check whether the same evidence closes a row on
[rc-505mk2.md](rc-505mk2.md) too. The ASSIGN vocabularies differ, so an ASSIGN
decode does **not** transfer between them.
