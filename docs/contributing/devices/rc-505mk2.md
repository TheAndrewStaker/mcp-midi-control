## Device

Boss's tabletop loop station: five stereo tracks, 99 memories, and a large
rhythm and effects section. Boss's companion app is the **RC-505mk2 Editor** or
Boss Tone Studio, depending on your platform.

Like the SPD-SX, this device has **two surfaces**, and both are useful:

| Surface | How | What it does |
|---|---|---|
| **Live MIDI** | USB or DIN MIDI | Memory recall by Program Change, and looper and track control through the memory's user-configured ASSIGN table |
| **Storage** | The unit mounted as a drive | Reading and authoring a memory's name and its ASSIGN control routings inside its stored files |

The important thing to understand about this device: **it never echoes state**.
There is no parameter read over MIDI at all. Nothing can be verified by asking
the unit; it is confirmed by ear, by the front panel, or by reading the stored
files back off the drive.

Support tier: `verified`. This mirrors `capabilities.support_tier` on the
descriptor at `packages/boss-rc/src/descriptor.ts`; the contribution gate fails if the two disagree.
The tier is set from this device's PRIMARY authoring surface, which is the FILE surface: hardware-confirmed through this server on the maintainer's own unit. Its live MIDI surface is documented-only. The tier now lives on the per-device config rather than the shared Boss RC factory, so this device and the RC-600 can differ, and they do.

## Before you start

Read [../SAFETY.md](../SAFETY.md) once. The device-specific parts:

- **The two surfaces need different states.** Live MIDI control needs the unit
  running normally. Reading or authoring memories needs the unit **mounted as a
  drive**. If a storage ask reports "not mounted", that is the mode, not a bug.
- **The unit never tells you anything.** There is no parameter read over MIDI, so
  a tool call that reports success has confirmed only that bytes went out. Your
  ears and the front panel are the verification, always.
- **ASSIGN routings are user-configured, and that is load-bearing.** A CC only
  does something if the loaded memory's ASSIGN table routes it. A CC that does
  nothing usually means the memory has no assign for it, not that the wire is
  wrong. Check the memory's ASSIGN page before reporting.
- **Authoring writes to stored memories.** The server takes a backup before a
  write and uses the device's own double-buffer, so a bad write is recoverable,
  but back up anyway.
- **Firmware updates.** Never run Boss's updater while an MCP host holds the port
  or the drive.
- **What we will never ask you to do.** No firmware modification, no opening the
  unit, no factory reset.

## Asks, ranked

### SESSION-1: Drive a looper CC through the server and watch the unit
**Tier: SESSION | ~10 minutes | sends MIDI only, nothing is stored | unlocks: end-to-end looper coordination**

The CC trigger itself is confirmed by ear. What has not been done is driving it
**through this server** and watching the looper respond.

First check which control channel your unit receives on, and make sure the
loaded memory has an ASSIGN routing the CC you are about to send. Then:

> "Send CC 80 at value 127 on my RC-505mk2's control channel."

Report: the control channel, the memory number, which ASSIGN slot maps that CC
and to what, and what the looper actually did.

If nothing happens, say what the memory's ASSIGN page shows. That distinguishes
"the wire is wrong" from "this memory has no assign", and those look identical
from outside.

### SESSION-2: Confirm memory recall lands where you expect
**Tier: SESSION | ~5 minutes | changes the loaded memory, nothing is stored | unlocks: recall confidence across the range**

Recall is confirmed, but the off-by-one is the kind of thing worth exercising at
both ends of the range: memory M recalls on Program Change M minus 1.

> "Switch my RC-505mk2 to memory 1."

then

> "Switch my RC-505mk2 to memory 99."

Report what the display showed for each. A one-off error at either end is a real
bug and would be invisible in the middle of the range.

### DONATE-1: Send a memory file from a different firmware
**Tier: DONATE | ~5 minutes | no device time | unlocks: cross-firmware codec confidence**

Mount your RC-505mk2 as a drive and copy off the stored file for one memory.

The codec and the ASSIGN dictionary are byte-exact against real device files,
but those files came from one unit on one firmware. Files from a second unit are
the cheapest possible check that the format does not drift.

Send the file plus your firmware version and a description of what the memory
actually contains: its name, and which ASSIGN slots are populated and with what.
The description is what turns the file into a check rather than just data.

### SESSION-3: Author a memory and confirm it on the unit
**Tier: SESSION | ~15 minutes | writes stored data, back up first | unlocks: authoring confidence beyond one unit**

Authoring is confirmed on the maintainer's unit. A second unit, especially on a
different firmware, exercises the double-buffer arbitration where drift would
show up first.

Back up first, then ask the server to author a name and one or two ASSIGN
routings into a memory you do not need. Unmount, restart the unit, and check the
memory on the front panel.

Report the memory number, the name and assigns you asked for, and what the unit
shows.

## Submitting

See [../SUBMITTING.md](../SUBMITTING.md). For this device, always include:

- RC-505mk2 firmware version,
- operating system,
- the memory number involved,
- **which surface you used**, live MIDI or the mounted drive,
- the control channel and the relevant ASSIGN routing, for any CC ask,
- what the unit did, since it never reports anything back.

## When an ask closes

1. Move the capability's row in **Support status** to its new status word and
   cite the new evidence.
2. Add a line to **Confirmed on hardware** if a device confirmed it.
3. Delete the closed ask from **Asks, ranked**, or reduce it to a one-line closed
   note if the RC-600 still needs it.
4. Update `capabilities.support_tier` and `capabilities.verification` on the
   descriptor if the tier moved. The tier lives on the per-device `BossRcConfig`,
   NOT on the shared factory, so changing it here does not touch the RC-600.
   Preflight fails if the page and the descriptor disagree.
5. Update this device's row in [../README.md](../README.md).

The RC-600 shares this device's stored-file generation and hybrid transport, so
check whether the same evidence closes a row on [rc-600.md](rc-600.md) too.
